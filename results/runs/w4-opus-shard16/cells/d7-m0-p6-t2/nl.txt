A container-ship crane yard is driven by two independent scheduling instances that share one common pool of stow cells; each instance runs its own worker cranes, and both instances' workers contend for the same cells. Access to the pool uses optimistic locking: to change a cell, a worker first reads the cell's current version number and remembers it as a snapshot, then later tries to commit its change. A commit succeeds only if the worker is currently a registered participant and its snapshot still equals the cell's live version, meaning nothing changed underneath it; committing bumps the cell's version by one and records the snapshot the write was based on. If the cell's version has moved since the worker read it, the worker's snapshot is stale, so it must retry by re-reading the current version before it can try again. The yard supervisor can revoke a worker's registration at any time, which cancels any in-flight attempt that worker held, and can re-register it later. The whole point of the version check is that a stale worker, one operating on an out-of-date snapshot, must never have its change silently take effect on the shared pool.
SAFETY PROPERTY: For every cell in the shared pool, the most recent committed change was based on the version immediately preceding the current one, so no stale worker's change ever took effect.
